**文档版本：V0.1**

**暂定产品形态：Web 网站**

---

# 1. 产品概述

## 1.1 产品定位

建立一个以**交互式地球地图**为主要入口的全球演出与活动资料平台。

用户进入网站后首先看到一个可旋转、可缩放的地球。世界各地已经收录的演出、综艺录制、晚会、音乐活动及其他相关活动，以节点形式分布在地图上。

用户可以从：

> 全球 → 国家 / 地区 → 城市 → 剧院 / 场馆 → 具体演出 / 活动

逐级缩放和探索。

例如：

```text
地球
↓
美国
↓
纽约
↓
Broadway
↓
Richard Rodgers Theatre
↓
某部音乐剧 / 某一场演出
```

或者：

```text
地球
↓
英国
↓
伦敦
↓
West End
↓
某剧院
↓
某一场音乐剧
```

中国地区：

```text
地球
↓
中国
↓
北京
↓
天桥艺术中心
↓
某音乐剧某场演出
```

网站不仅用于查看“最近有什么演出”，同时希望成为一个可以长期积累的：

> **全球演出地图 + 活动档案库 + 补课资料库 + 用户共同维护社区**

用户可以通过时间、地点、演出名称、人物和关键词找到过去发生过的活动，并查看其他用户整理的照片、短视频、文字资料、外部链接、代码 / Repo 等内容。

---

# 2. 产品核心目标

产品希望解决三个核心问题。

## 2.1 用地图直观探索全球演出

传统演出资料通常按照文章、列表、社交媒体帖子等形式分散存在。

本网站希望建立一种更直观的空间结构：

```text
世界
→ 国家
→ 城市
→ 剧院
→ 演出
```

让用户能够通过地理位置自然探索演出。

---

## 2.2 建立长期可检索的演出资料档案

活动结束之后，资料往往散落在：

* 微博；
* B站；
* YouTube；
* 小红书；
* GitHub；
* 新闻网站；
* 官方公众号；
* 用户个人相册；
* 网盘或其他社区。

网站允许用户围绕具体活动整理：

* 基本活动信息；
* 剧院信息；
* 演出时间；
* 演员；
* 海报；
* 照片；
* 短视频；
* Repo；
* 外部资料链接；
* 文字补充；
* 评论和讨论。

从而形成结构化的历史档案。

---

## 2.3 支持社区共同维护

由于全球演出与活动数量极大，不可能由单个管理员长期手工维护。

因此平台需要支持：

```text
注册账号
↓
用户投稿
↓
系统查重
↓
提交审核
↓
管理员 / 社区审核
↓
正式加入地图
```

最终形成一个用户共同维护的数据平台。

# 5. 首页：交互式地球

## 5.1 首页基本形式

打开网站后直接展示一个三维或视觉拟真的地球。

地球支持：

* 鼠标拖动旋转；
* 触摸拖动；
* 滚轮缩放；
* 自动缓慢旋转；
* 点击国家；
* 点击城市；
* 点击活动节点；
* 点击节点聚合。

地球视觉可以包括：

* 深蓝色海洋；
* 绿色 / 土黄色大陆；
* 极地颜色；
* 经纬线；
* 昼夜明暗；
* 昼夜分界线；
* 夜晚侧城市灯光；
* 蓝色大气层光晕；
* 星空背景；
* 活动节点脉冲效果。

这些主要用于建立网站独特的视觉身份。

# 6. 多级地图缩放体系

网站地图不是简单的“一个地球加几个点”，而应该随着缩放等级切换信息粒度。

---

## Level 1：全球视角

显示：

* 地球；
* 国家轮廓；
* 大型活动聚合节点；
* 全球活动密度。

例如：

```text
中国  3,251
美国  2,438
英国  1,735
法国    846
意大利  531
```

此时不显示所有具体场馆。

---

## Level 2：国家 / 地区视角

继续放大，例如进入：

* 中国；
* 美国；
* 英国；
* 法国；
* 意大利。

地图开始显示：

* 主要城市；
* 活动数量；
* 城市聚合节点。

例如美国：

```text
New York     813
Los Angeles  241
Chicago      137
...
```

---

## Level 3：城市视角

例如：

* 北京；
* 上海；
* 纽约；
* 伦敦；
* 巴黎；
* 米兰。

开始显示具体：

* 剧院；
* 演播厅；
* 体育馆；
* 音乐厅；
* 活动场馆。

纽约可以进一步突出：

> Broadway

伦敦可以突出：

> West End

---

## Level 4：场馆视角

地图上直接显示剧院节点。

例如：

```text
上海文化广场
天桥艺术中心
北京保利剧院
Majestic Theatre
Gershwin Theatre
Palace Theatre
...
```

点击场馆进入场馆页面。

---

## Level 5：演出 / 活动视角

一个场馆可以拥有很多历史活动。

例如：

```text
上海文化广场

2026
├─ 7月：《XXX》
├─ 6月：《XXX》
└─ 5月：《XXX》

2025
├─ ...
```

点击具体活动进入活动详情。

---

# 7. 节点自动聚合与展开

活动数量较多时，不应一次显示几千个点。

系统应根据缩放等级自动聚合。

例如全球视角：

```text
● 126
```

表示某一区域存在 126 个活动。

放大：

```text
● 北京 78
● 天津 21
● 石家庄 27
```

继续放大：

```text
● 天桥艺术中心 16
● 国家大剧院 11
● 保利剧院 7
```

最终展开为具体活动节点。

点击聚合节点时：

> 地图自动平滑放大到该区域。

# 9. 活动 Event

活动是整个系统最重要的数据实体。

一条活动记录建议包含：

```text
活动名称
活动类型
作品 / 节目名称
开始时间
结束时间
国家
城市
场馆
经纬度
演员 / 嘉宾
制作方
活动简介
官方页面
海报
标签
投稿用户
审核状态
创建时间
更新时间
```

需要区分：

## 作品

例如：

> RENT

## Production / 制作版本

例如：

> RENT 2026 中国巡演版

## Event / 具体场次

例如：

> RENT 2026-08-07 19:30 北京场

这样可以避免把“一个作品”和“一次具体演出”混成同一条数据。

# 11. “补课”资料系统

这是网站区别于普通演出地图的重要功能。

用户查看一个已经结束的活动时，可以直接看到其他用户整理的相关资料。

资源类型：

## 图片

例如：

* 官方海报；
* 剧照；
* 用户现场照片；
* 节目单；
* 媒体截图。

---

## 短视频

例如：

* 现场片段；
* Curtain Call；
* Interview；
* 排练片段；
* 官方宣传片。

第一阶段建议限制：

```text
≤ 60 秒
≤ 50 MB
```

避免变成视频平台。

---

## 外部链接

允许提交：

* Bilibili；
* YouTube；
* 微博；
* 新闻页面；
* 官方页面；
* 豆瓣；
* 小红书；
* 采访；
* 其他资料。

---

## Repo

部分活动可能存在：

* 数据整理仓库；
* 字幕项目；
* 资料归档项目；
* GitHub Repo；
* 代码；
* 数据集。

因此资源类型中可以专门支持：

```text
Repository
```

例如：

```text
GitHub
GitLab
Gitee
其他 Repo
```

---

## 文字笔记

用户可以整理：

* 背景介绍；
* 时间线；
* 卡司变化；
* 历史资料；
* 观演记录；
* 补课指南。

```text

类型

描述

对象存储

图片
短视频
```

第一阶段建议：

### 图片

单个用户每个活动：

```text

```

上传前自动：

* 限制格式；
* 压缩；
* 生成缩略图。

---

### 视频

单个用户每个活动：

```text
≤ 1～3 个
≤ 60 秒
≤ 50 MB / 个
```

第一阶段优先支持：

```text
MP4
WebM
```

# 20. 重复活动检测

用户投稿时系统需要自动搜索可能重复的记录。

主要根据：

```text
活动名称
+
场馆
+
日期
+
时间
```

判断。

例如系统提示：

> 可能已经存在以下活动，请确认是否重复。

避免多人重复创建相同节点。

# 42. 最重要的产品原则

## 原则一：活动必须结构化

不能把网站做成：

> 地图 + 用户帖子。

真正核心应该是：

```text
一个真实 Event
↓
所有用户围绕这个 Event 补充资料
```

否则很快会变成重复且不可检索的信息流。

---

## 原则二：作品、Production、Event 必须分离

例如：

```text
RENT
作品

RENT 中国巡演 2026
Production

2026-08-07 北京 19:30
Event
```

这是数据库长期能否维护好的关键。

---

## 原则三：地点同样必须结构化

不要只保存：

```text
“北京某剧院”
```

而应该形成：

```text
Country
↓
City
↓
Venue
↓
Event
```

这样地球才能自然支持不同缩放层级。

---

## 原则四：资料依附于活动，而不是散落成帖子

例如：

```text
RENT 2026 北京场
├─ 官方海报
├─ 用户 A 照片
├─ 用户 B 视频
├─ 用户 C 补课链接
├─ 用户 D Repo
└─ 评论
```

长期查询体验会远好于传统时间线社区。

# 45. 当前建议的开发主线

接下来开发优先级建议固定为：

```text
① 地球视觉和地图层级
        ↓
② Country / City / Venue / Event 数据模型
        ↓
③ 搜索与筛选
        ↓
④ Supabase 数据库
        ↓
⑤ 用户账号 + 我参加过
        ↓
⑥ 用户投稿 + 审核
        ↓
⑦ 图片 / 视频 / Link / Repo
        ↓
⑧ 评论与举报
```

在第②步的数据模型没有稳定之前，不建议急着做复杂社区功能。

因为整个产品长期是否好维护，最关键的并不是地球渲染，而是：

> **作品—版本—场次—场馆—城市—人物—资料之间的结构是否设计正确。**
